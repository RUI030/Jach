# Handoff: the 20-task baseline (2026-11-19)

You are running a baseline on another machine. The goal is to measure how well **untrained** local models build small
full-stack web apps, with no Jac help and with the Jac skill files, before any Jac training. Nothing here needs a
design decision from you. Run the arms in order, keep every run directory, and report the summary.

## 1. The experiment

Run the arms in this order. Every arm runs all 20 tasks, 3 rounds each (60 runs per arm).

| Order | Model (untrained) | Arm | What the model gets |
|---|---|---|---|
| 1 | Ornith-1.5-9B, `Q8_0` | `any` | Empty folder, any language and framework, no skills, no MCP |
| 2 | Ornith-1.5-9B, `Q8_0` | `jac` | Jac scaffold + template, the 40 Jac skill files, no MCP |
| 3 | Qwen3.5-27B (dense) | `jac` | Same as arm 2 |
| 4 (optional, if time allows) | Qwen3.5-27B (dense) | `any` | Same as arm 1. Separates "bigger model" from "Jac" |

A trained Jac model is out of scope for this handoff.

Fixed for every arm, so only the model and the arm differ:

- Harness: pi (`pi -p`), thinking `medium`, context 65,536, max output tokens per turn 16,384.
- Time limit: 30 minutes for the agent per run (`TIMEOUT=1800`). The gate has its own 15-minute limit.
- Same task specs, same browser actions, same prompts (written by `run.sh`).
- Run one model at a time on the GPU, one run at a time. Parallel runs slow each other and make the seconds column meaningless.

## 2. Where everything is

Repository: `git@github.com:RUI030/Jach.git` (branch `main`). Every path below is relative to the repository root.

| What | Where |
|---|---|
| The 20 tasks, Jac version | `jach/tasks/<id>.json`: the goal names the nodes and fields; only `server.jac`, `frontend.jac`, `main.jac` may change |
| The 20 tasks, any-stack version | `jach/tasks/any/<id>.json`: same actions, the goal names no Jac types, the app starts with `sh start.sh` |
| Task index: levels, easy/hard, which open-source apps the new tasks come from | `jach/tasks/README.md` |
| Reference solutions (9 of the 20 tasks only) | `jach/tasks/reference/<id>/` |
| Jac project template (the three files put on top of the `jac create` scaffold) | `jach/template/` |
| The gate: Jac checks + browser actions + restart | `jach/core/gate.jac`, `jach/core/browse.jac`, `jach/core/check.jac` |
| Baseline scripts | `benchmark/baseline/run.sh` (one run), `run_all.sh` (one arm), `collect.py` (results) |
| Jac skill files given to the `jac` arm (exported from jac 0.36.1) | `benchmark/baseline/skills/` |
| Earlier baseline (2026-11-18, 2 tasks, 9B, pi/opencode/jach): background only | not in git; summarized in section 6 |

Spec fields: `id`, `level` (1 to 5), `difficulty` (`easy` = level 1–2, `hard` = level 3–5), `title`, `goal` (the
requirement given to the model), `writes`, `actions` (browser steps), and `inspired_by` on the 8 new tasks.

Action verbs: `open`, `fill <placeholder> <text>`, `click <label>`, `press <key>`, `wait <seconds>`,
`expect <text>`, `expect_not <text>`. Actions run in order on one fresh data store. The server is restarted before
the last action, so the last action checks that data was really stored.

## 3. Machine setup

Needs: an NVIDIA GPU, Linux, `bwrap`, Python 3, Node (for the scaffold), and these exact versions.

| Tool | Version | Notes |
|---|---|---|
| jac (jaclang) | 0.36.1 | `jac --version`. Not on PyPI; see `docs/CLOUD_GPU.md` in the JacLLM repo for installing it. `jac browse` must work (it drives the headless browser) |
| pi | 1.0.4 | `pi --version` |
| llama.cpp `llama-server` | b10840 or newer | Any OpenAI-compatible server works if it serves the model under the alias you pass as `MODEL_ID` |

Models (GGUF, from Hugging Face):

| Model | Repo | File | VRAM |
|---|---|---|---|
| 9B | `ornith-ai/Ornith-1.5-9B-GGUF` | `Ornith-1.5-9B-Q8_0.gguf` (~9.5 GB) | fits 16 GB |
| 27B | `unsloth/Qwen3.5-27B-GGUF` | 48 GB card: `Qwen3.5-27B-Q8_0.gguf` (~29 GB). 32 GB card: `Qwen3.5-27B-Q6_K.gguf` (~22 GB) | does not fit 16 GB |

Use the largest quant that fits with a 64k context, and write the quant you used in your report: a 27B at `Q6_K`
next to a 9B at `Q8_0` is a difference the reader must know about.

Serve one model at a time, on port 8791:

```bash
llama-server -m <path to gguf> --alias ornith-1.5-9b --jinja -c 65536 -ngl 99 --port 8791
```

```bash
llama-server -m <path to gguf> --alias qwen3.5-27b --jinja -c 65536 -ngl 99 --port 8791
```

Check it: `curl -s http://127.0.0.1:8791/v1/models` lists the alias.

## 4. Running

From the repository root. `MODEL_ID` must equal the `--alias` of the running server.

Smoke test first (about a minute each); both must print `"browser": "passed"`:

```bash
MODEL_ID=ornith-1.5-9b OUT_ROOT=/tmp/smoke benchmark/baseline/run.sh any level1-hello 1
```

```bash
MODEL_ID=ornith-1.5-9b OUT_ROOT=/tmp/smoke benchmark/baseline/run.sh jac level1-hello 1
```

The first `jac` run also builds the scaffold once (`jac create project --use jac-shadcn`, cached in `~/.cache/jbw/_scaffold`).

Then the arms, in order. Each call runs 20 tasks x 3 rounds, round by round, easiest task first, and skips runs that
already have a `gate.json`, so after a crash you rerun the same command:

```bash
MODEL_ID=ornith-1.5-9b benchmark/baseline/run_all.sh any 3
```

```bash
MODEL_ID=ornith-1.5-9b benchmark/baseline/run_all.sh jac 3
```

Stop the 9B server, start the 27B one, then:

```bash
MODEL_ID=qwen3.5-27b benchmark/baseline/run_all.sh jac 3
```

Before the 27B arm, time one run (`run.sh jac level2-todo 1`) and compare its seconds and output tokens with the 9B
run of the same task, so the time estimate in section 5 can be corrected early.

Results go to `runs/baseline/<MODEL_ID>/<arm>-<task>-r<round>/` (`runs/` is git-ignored). Run `collect.py` after each arm:

```bash
python3 benchmark/baseline/collect.py runs/baseline
```

## 5. What is measured and what is screenshotted

Per run, `run.sh` keeps:

| File | Content |
|---|---|
| `meta.json` | arm, model, task, round, level, difficulty, harness settings |
| `prompt.txt` | the exact prompt the model got |
| `agent.jsonl`, `session/`, `agent.err` | pi's event stream and session log (every tool call and message) |
| `exit.txt` | `exit=` (0 finished, 124 timeout) and `seconds=` |
| `files.txt`, `project/` | every file in the finished project (without `node_modules`, `.venv`, `.jac`) |
| `gate.json` | Jac checks (`jac` arm: compile, wiring, descriptions) and each browser action's status and failure message |
| `shots/00-load.png` | the page right after the server starts and `/` is opened |
| `shots/NN-<action>.png` | the page at the end of each action; if the action failed, at the step where it failed. The last one is after the server restart |

`collect.py` turns these into `runs.json` (one row per run) and `summary.md`. The numbers to report:

1. **Task passed**: every action passed. Report per model x arm, split easy (9 tasks) and hard (11 tasks), out of 3 rounds.
2. **Actions passed**: partial credit, out of all actions.
3. **App started**: `/` answered within the gate's wait. A run that never starts fails every action for that reason only.
4. **Kept after restart**: the last action passed.
5. **Agent outcome**: finished or timeout; seconds; turns; output tokens; largest context.
6. **`jac` arm only**: the three Jac checks, whether the model read any skill (`skills_read`), and any non-Jac code or commands it fell back to (`nonjac_*`).
7. **`any` arm only**: the stack the model chose (`stack`: file extensions).

## 6. Expected time, and what happened last time

Measured on 2026-11-18 (9B `Q8_0` on an RTX 5080, pi): about 65–70 output tokens per second including prompt processing.

| Run kind | Seconds measured |
|---|---|
| `any`, easy tasks | 21–86 |
| `jac`, easy tasks | 134–664 |
| hard tasks | not measured; expect many to reach the 30-minute limit |

Estimate for one round of 20 tasks: 9B `any` about 2–3 h, 9B `jac` about 5 h, 27B `jac` about 6–7 h on a 32 GB
card (`Q6_K`) or 10–13 h on a 48 GB card (`Q8_0`), plus 1–2 min of gate per run. The upper bound is 10 h per arm per
round (20 x 30 min). Three rounds of the three arms: about 2–3 days on one GPU.

Earlier results on the two tasks it covered: 9B `jac` arm with pi passed 2 of 8 runs; 9B `any` arm with pi passed 3 of
4. One run per task is not enough to compare arms, which is why every task runs 3 rounds.

## 7. Known caveats (put them in the report)

- The `any` arm starts from an empty folder, so a failure there can be a setup failure (installing packages,
  writing `start.sh`) rather than a missing feature. Look at `00-load.png` and the "did not start" messages.
- The Jac goals name the node types and fields (`Task`, `Card`, `PaidBy`, ...); the `any` goals describe the data in
  plain words. This gives the `jac` arm slightly more guidance.
- 11 of the 20 tasks have no reference solution yet (`level1-hello`, `level3-booking`, `level4-order` and the 8 tasks
  added on 2026-11-19), so a task that no run passes may have a fault in its spec. If every run of every arm fails
  the same action of one task, report it as a possible spec fault instead of a model result.
- On jac 0.36.1, `jac test` leaves postgres databases under `~/.cache/jac/pg/`; check free disk space between arms.
